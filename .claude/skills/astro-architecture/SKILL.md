# Astro Architecture & Project Structure

## The required layout

Astro is opinionated about very little, but every project needs:

```
public/*             — unprocessed static assets, copied as-is
src/*                — your source code
src/pages/            — REQUIRED: file-based routes (see astro-pages skill)
package.json
astro.config.mjs      — recommended
tsconfig.json         — recommended
```

`src/pages/` is the **only** reserved directory. Everything else under `src/` (`components/`, `layouts/`, `styles/`, `content/`, `lib/`, `utils/`) is community convention, not an Astro requirement — organize it however suits the project.

### A typical mid-size project tree

```
public/
  robots.txt
  favicon.svg
src/
  assets/            (images/fonts to be processed — see astro-fonts skill)
  components/
    Header.astro
    Button.jsx
  content/           (content collection entries — see astro-content-collections skill)
    blog/
  layouts/
    BaseLayout.astro
    PostLayout.astro
  pages/
    index.astro
    about.astro
    posts/
      [id].astro
    api/
      hello.ts       (see astro-api-endpoints skill)
  styles/
    global.css
  lib/ or utils/     (framework-agnostic helper code, data fetching, etc.)
  middleware.ts       (see astro-middleware skill)
  content.config.ts   (see astro-content-collections skill)
  env.d.ts
astro.config.mjs
tsconfig.json
package.json
```

## `public/` vs `src/`

- **`public/`** — files copied verbatim into the build output. No processing, no bundling, no optimization. Right for `robots.txt`, `manifest.webmanifest`, files that must be at a fixed, predictable URL, or assets referenced by absolute path from outside Astro's build pipeline. CSS/JS placed here is **not** bundled or optimized.
- **`src/`** — everything Astro processes: components, layouts, styles, Markdown, and images that should go through Astro's image optimization. As a rule, any CSS or JS you author yourself belongs in `src/`, not `public/`.

## Key conventional subdirectories

- **`src/components/`** — reusable `.astro` components and/or UI-framework components (`.jsx`, `.svelte`, `.vue`, ...). Group by feature or by type, whichever scales better for the project size.
- **`src/layouts/`** — Astro components that wrap page content with shared structure (`<html>`, `<head>`, nav, footer). Layouts can nest — a `PostLayout.astro` might wrap its children in a shared `BaseLayout.astro` to add site-wide chrome while handling post-specific markup (title, author byline) itself.
- **`src/styles/`** — global stylesheets, CSS resets, design tokens, Tailwind entry files. See the astro-scoped-styling skill for per-component CSS.
- **`src/content.config.ts`** — the single file that defines all content collections via `defineCollection()`. See the astro-content-collections skill.
- **`src/middleware.ts`** (or `src/middleware/index.ts`) — the one middleware entrypoint that runs before every route. See the astro-middleware skill.
- **`src/env.d.ts`** — extend global TypeScript types here: `ImportMetaEnv` for custom env vars, `App.Locals` for middleware-set data.

## Configuration files

- **`astro.config.mjs`** (`.js`/`.ts` also supported) — integrations, adapter, `output` mode, `fonts`, `env` schema, `scopedStyleStrategy`, and most other project-wide behavior. This is the single source of truth for how the project builds and renders.
- **`tsconfig.json`** — generated by every starter; needed for full editor tooling (path aliases, npm package types) even in JS-only projects.
- **`package.json`** — standard `dev`/`build`/`preview` scripts wired to `astro dev` / `astro build` / `astro preview`.

## The rendering mental model

Astro's core architectural idea is **HTML-first, JS opt-in, at every layer**:

1. **Pages and components render to static HTML by default.** No client runtime ships unless you explicitly ask for one. This is true whether the page is built once (prerendered, the default) or rendered per-request (on-demand/SSR, opt-in via an adapter — see the astro-server-side-rendering skill).
2. **Client islands** (`client:*` directives on framework components) opt individual components into browser hydration, each with independent load timing. See the astro-client-islands skill.
3. **Server islands** (`server:defer`) opt individual components into deferred, per-request server rendering *inside* an otherwise static/cacheable page. See the astro-server-islands skill.
4. **Middleware** runs on the server for every request (build-time for prerendered routes, request-time for on-demand ones) and can inject shared data via `Astro.locals`. See the astro-middleware skill.
5. **Content collections** are the typed, validated data layer for local or remote structured content (Markdown, JSON, YAML, or live/remote sources), separate from routing — you still need a page under `src/pages/` to turn a collection entry into a URL. See the astro-content-collections skill.

The practical decision this model forces on every new piece of UI: **does this need to run in the browser?** If no, write a plain `.astro` component. If yes, is it a framework component that needs a `client:*` directive, or can a `<script>` tag with `addEventListener`/a custom element do the job more cheaply? (See the astro-scripts-event-handling skill.)

## Choosing prerendered vs. on-demand per route

Astro's default output mode (`'static'`) prerenders everything at build time; you opt individual routes into on-demand rendering with `export const prerender = false` once an adapter is installed. Flip the default with `output: 'server'` and opt individual routes *out* with `export const prerender = true` instead. Prefer starting in `'static'` mode and opting out route-by-route — it's the more performant default, and mixing modes per-route is fully supported (this used to be called "hybrid" output; as of Astro 5 it's just `'static'` with per-route opt-outs). Full detail in the astro-server-side-rendering skill.

## Organizing for scale

- **Feature folders over type folders**, once a project grows past a handful of pages: `src/features/checkout/{Checkout.astro,CheckoutForm.tsx,checkout.config.ts}` colocates everything about one concern instead of scattering it across `components/`, `lib/`, and `pages/`.
- **Keep `src/pages/` thin.** Route files should mostly compose layouts + components + a data fetch (via `getStaticPaths`, `getCollection`, or a fetch call) — push real logic into `src/lib/`/`src/utils/` or into the components themselves so it's testable and reusable outside the routing layer.
- **One `content.config.ts`, one `middleware.ts`.** Both are singular by design — don't try to split them per-feature; instead compose multiple collections/middleware functions (`sequence()`) inside the one file.
- **Co-locate schemas with content collections**, not scattered Zod types — content.config.ts is the canonical source of truth for a collection's shape and should be the only place that shape is declared.
